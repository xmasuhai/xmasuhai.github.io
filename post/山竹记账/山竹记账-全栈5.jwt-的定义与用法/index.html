Session + Cookie

1. 前置知识：Cookie ⇧

  • Cookie 属于 HTTP 协议
    • 功能是由服务器 Server 向客户端 Client（浏览器） 发送的一段 Token
    • 这个Token必须在访问同域名网站后续的所有请求中的请求头自动带上

2. 前置知识：Session ⇧

  • Session 是一般基于 Cookie 实现的技术
    • Server 发送给客户端 Client，用来识别不同客户端请求
    • HTTP 是无状态的，本身无法区分不同客户端用户的请求
    • 在服务器中根据客户端请求带上的 Cookie 来识别
  • 带来的问题是：
    • 使用明文的Cookie，会难以处理用户身份伪造的攻击
  • 用户的信息Cookie存在服务器内存或文件（Redis）中，使用随机数生成密文的Cookie可以解决
    • 服务器可以识别用户
    • 用户无法篡改Cookie
  • 这个保存在服务器内存或文件中，用来跟Cookie做一个对应关系，就是Session
  • 由于需要保存到内存或文件中，需要占据服务器的资源，来认证用户

3. JWT 的定义 ⇧

  • 服务器发送给客户端的密文信息中包含部分用户信息，服务器可以解密客户端请求中携带的密文，从而识别用户
  • 用户无法篡改密文
  • 并没有将用户信息缓存到服务器上，而是存储在密文中

JWT 的结构 ⇧

  • Header 标题
    • 必须标记加密算法 {"alg": "HS256", "typ": "JWT"}
    • 头部字段表可参考 Standard fields 标准字段
    • 常用字段有 alg、exp、typ 等
    • 一般需要使用 base64 处理一下特殊字符
  • Payload 载荷
    • 可用来存储非敏感的用户数据
    • 一般需要使用 base64 处理一下特殊字符
  • Signature 签名（真正加密部分）
    • Signature = 加密算法(私钥 + base64(Header) + base64(Payload))
  • 完整的 JWT 就是 Header.Payload.Signature 三部分连接
  • 精髓就是 JWT = 加密(uid) 给前端

和 Session & Cookie 的区别就是

  • Session & Cookie 将uid 存到内存对应表，把key发给前端
  • JWT 将 uid 存到密文，把密文发给前端

4. JWT 的用法 ⇧

区别于 Session & Cookie 的用法

  • 前端发送请求 POST /session，包含用户名、密码等信息，接受返回的响应中的 Cookie
  • 之后的所有请求都自动带上这个 Cookie，例如发送请求 GET /user，服务器找到对应用户数据返回
  • Cookie 是浏览器自动维护的

JWT 的操作

  • 前端发送请求 POST /session，包含用户名、密码等信息，接受返回的响应中的 JWT
  • 前端无需解密或分析识别 JWT 中的信息
  • 前端需要将JWT存储到浏览器的 Storage 中
  • 并且需要手动维护所有的请求头，常配合使用 axios 之类的库，将之后其他所有的请求的 header 都带上 JWT
    • Authorization 的字段中
  • 此时例如发送请求 GET /user，服务器判断请求头中是否存在 Authorization
  • 有则会去解密 JWT，验证签名，即验证 Signature 这部分解密后是否等于 Payload
  • 验证通过后再根据 Signature 中解密的 uid 去查询数据库中的用户信息，实现认证用户，再进行后续操作

JWT 也可以同时存放到 Cookie 中，是否多此一举

  • Cookie 是 HTTP 协议的内容，而 JWT 也使用于其他通信协议，比如 UDP、RPC、WebSocket
  • JWT 比 Session & Cookie 更通用，并不强制使用 HTTP
  • JWT 是做 Web 认证的，并不单单做 HTTP 认证

5. JWT概览 ⇧

Session & Cookie

  • 服务器无法通过无状态的 HTTP 请求来分辨不同用户，需要一种技术来标记用户
    • 标记用户，区分各个请求发送的用户身份
  • 使用 Cookie 来标记用户，可以识别请求来源是否为同一个用户
  • 用户发送身份验证请求，服务器返回响应头中添加 Set-Cookie 响应标头
  • 之后所有该用户请求都自动带上该Cookie
  • 客户端可识别后续请求中携带的 Cookie，从而识别用户
  • Cookie 就是服务器发送给客户端的字符串，浏览器下次再发起同域名的请求时，必须带上这个字符串
  • Cookie 使用较长（例如128）位随机数，防止用户篡改
  • 服务器将 Cookie 存储在内存中，对应不同的用户信息，即为 Session 会话
  • Session 通过 Cookie 实现，Session 的key下发客户端
  • Session 对用户规模而增大，占据系统资源，依赖服务器的状态

JWT

  • 服务器无状态，发送加密字符串给用户，后续用户请求携带这个加密字符串
  • 加密字符串可以存在 Cookie 中，这样只适用于 HTTP 协议
  • 加密字符串存在其他请求头字段中（例如 Authorization）可适用于其他协议
  • 服务器只需要根据密钥，来解密这个字符串，成功验证后，根据解密的用户信息查询数据
  • 客户端无需解密，只需要保证后续请求都携带即可；客户端不可直接读取，应为加密字符串有可能过期
  • 例如前端需要用户信息，发送请求询问服务器，由服务器来认证
  • 这个满足一定规则的加密字符串即为 JWT
  • 好处是节省服务器空间
  • 并且不需要做一个集群来同步存储登录信息，任何部署的服务器都可以只需通过密钥给任何用户进行认证
  • 一旦成功解密JWT就认证成功

JWT 的问题

  • 无法直接对用户进行 Block 操作
  • 例如禁用某个用户登录或其他操作，服务器接受多个用户的 JWT，无法直接禁用
  • JWT 解密出的信息都相同时，无法区分状态
  • 除非引入状态，通过一个黑名单存储等方法来实现

  • 使用加密部分，即签名来验证前两部分是否正确，防止被篡改

  • 对服务器存储空间要求降低，只用存储 secret 密钥

  • 虽然前端可解开base64信息，但不允许直接读取 JWT 中数据，只能拿它作为凭证，向服务器请求数据

    • 原则就是前端永远只相信后端的数据，后端永远不相信前端传的数据
    • 防止用户伪造数据，或者过期数据

  • 因为JWT数据是不可信的，只有通过服务器验证后，才可获取响应数据

7. JWT 过期时间 ⇧

  • Standard claim fields 标准的声明字段中使用 exp 表示过期时间，记录在 Payload 中
  • 要求为一个时间戳数字，推荐以几小时作为过期的期限，尽快过期，安全
  • 一般需要配合 Refresh Token 更新令牌使用，用来续期/换票

8. JWT 与 Refresh Token ⇧

  • 一旦在请求中发现 JWT 过期了，根据同时发送的 Refresh Token 来验证是否发送更新令牌
  • Refresh Token 的有效期更长，需要使用的次数更少
  • JWT 频繁使用，但有效期短，相对安全；
  • 都需要配合HTTPS加密通信，不然有可能会中间人攻击拦截
  • 密文还需要防止重放攻击，使用唯一的id来区分请求，服务器直接拒绝相同请求
