1. 如何处理JWT过期 ⇧

目前的jwt，没有过期功能，用户可以无限期的使用

  • 防止 jwt 泄漏，或者用户被其他用户利用，需要添加过期功能
  • 过期一般设置 2h~24h
  • 需要在原本的 payload 中添加标准字段属性 exp: (Time.now + 2.hours).to_i，转成秒数数字，非毫秒数
  • payload = {user_id: self.id, email: self.email, exp: (Time.now + 2.hours).to_i}
  • 在AutoJwt中间件解码时，无需添加验证是否过期的逻辑 epx = payload[0]["exp"]
    • 在JWT.decode解码是自动判断是否过期，如果过期，则会走 rescue nul 的逻辑，即payload为空
    • 使用高级的 rescue 写法，可明确提示是哪一种报错：过期或被篡改
  • 有些接口是无需jwt检查的，需要添加 api 白名单，可绕过验证 jwt

class User < ApplicationRecord
  validates :email, presence: true

  # User 自己生成 JWT.
  # @return [String]
  def generate_jwt
    payload = { user_id: self.id, email: self.email,
      exp: (Time.now + 2.hours).to_i }
    hmac_secret = Rails.application.credentials.hmac_secret
    JWT.encode(payload, hmac_secret, "HS256")
  end

  # 生成 JWT 的 HTTP 头.
  # @return [Hash]
  def generate_auth_header
    { "Authorization": "Bearer #{self.generate_jwt}" }
  end
end

require "set"

class AutoJwt
  # 初始化中间件.
  # @param [Object] app Param documentation.
  # @return [Object]
  def initialize(app)
    @app = app
  end

  # 从请求头中获取 jwt，并解析.
  # @param [Object] env Param documentation.
  # @raise [StandardError]
  # @return [Array]
  def call(env)
    # 跳过 JWT 解析
    return @app.call(env) if SKIP_JWT_PATHS.include?(env["PATH_INFO"])

    header = env["HTTP_AUTHORIZATION"]
    if header.present?
      jwt = header.split(" ")[1] rescue ""
      begin
      payload = JWT.decode jwt, Rails.application.credentials.hmac_secret,
        true, { algorithm: "HS256" }
      rescue JWT::ExpiredSignature
        return [ 401, {},
          [ JSON.generate({ reason: "Unauthorized, Token expired" }) ] ]
      rescue
        return [ 401, {},
          [ JSON.generate({ reason: "Unauthorized, Invalid JWT" }) ] ]
      end
      env["current_user_id"] = payload[0]["user_id"] rescue nil
    end
    @status, @headers, @response = @app.call(env)
    [ @status, @headers, @response ]
  end

  # 定义白名单常量，使用 %w[...] 写字符串数组更简洁
  # .freeze 防止内容被篡改；Set#include? 的查询时间复杂度是 O(1)，比数组的 O(n) 更快
  SKIP_JWT_PATHS = Set.new(%w[
    /api/v1/session
  ].freeze)
end
  • 此处返回值中状态吗不可以写成 :unauthorized，只能写数字 401，或者 Rack::Utils.status_code(:unauthorized)
  • Rack 中间件返回的状态码必须是整数
    • Rack 3.2.7 在构造测试响应时调用了 status.to_i
    • 但 Ruby 的 Symbol 没有 to_i，因此 get 就抛出了 NoMethodError

3. Refresh Token 是什么 ⇧

核心要点 ⇧

  • 问题背景：
    • JWT 设置较短有效期（如 2 小时）以保证安全，但过期后要求用户重新登录体验差；
    • Refresh Token 用于在 JWT 过期后无需用户重新登录即可自动获取新的 JWT
    • JWT 过期后，发送刷新令牌请求，凭 Refresh Token 请求续期接口换取新 JWT；
    • 只有 Refresh Token 失效时，才需要重新登录。
  • 两类 Token 定位不同：
    • JWT 用于用户认证，有标准：JWT spec RFC 7519；
    • Refresh Token与 JWT 完全独立：用于 JWT 续期，没有明确标准格式
    • 需自行设计随机数存表，存入数据库、Redis 等存储介质（有状态）
    • 也可以和 JWT 采取相同的无状态机制
  • Refresh Token 本质：服务端在登录时额外下发的一个随机字符串（或者和 JWT 相同的加密字符串）
    • 存储在数据库的 Refresh Token 表中，记录了用户 ID、随机数值和创建时间
  • 自动续期 vs 登录控制：
    • 通过 Refresh Token 数据库记录控制的是自动续期的设备数，而非同时登录的设备数
    • JWT 是无状态的，服务端不记录下发了多少个，无法控制登录数
  • 多设备各自持有独立的 Refresh Token，互不影响；可通过数据库记录，来限制自动续期的设备数量
  • 有效期按使用频率与被盗风险设计：
    • JWT 使用频繁、易被盗，有效期短；
    • Refresh Token 使用频率低，有效期可更长，但一般不超过一个月；
    • 可通过重置功能清空该用户所有已下发的 Refresh Token 兜底

重要细节 ⇧

1. 基本续期流程 ⇧

  1. 用户登录 → 服务端下发 JWT（有效期 2 小时）+ RefreshToken（有效期如 7 天）
  2. Refresh Token，存入 Refresh Token 表（RT 表）；加密字符串可包含信息：所属用户、随机数、过期时间、下发的完整时间
  3. JWT 过期后，前端不提示用户重新登录，而是携带 Refresh Token 请求续期接口 /api/v1/refresh_token
  4. 服务端校验 Refresh Token 有效后，下发一个新的 JWT，用户继续访问
  5. 7 天内可反复续期；第 7 天 Refresh Token 也过期时，才提示用户重新登录
  6. 重新登录后获得新的 JWT 和新的 Refresh Token，循环往复

2. 多设备 / 多次登录的 Refresh Token 处理 ⇧

  • 用户在不同设备或不同时间登录，每次得到的 Refresh Token 应该不同，可以各自续期。
    • 如何相同，可能会出现极端情况：两次登录间隔恰好 7 天，第二次登录拿到的 Refresh Token 立刻就过期了，显然不合理。
  • 数据库中每个 Refresh Token 占据一条数据库记录，分别记录各自的创建时间和所属用户。
  • 可通过 Refresh Token 的数据库控制同时自动续期的个数；个数、天数都不写死
  • 一个设备的 Refresh Token 过期不影响其他设备：谁过期谁登录，不同的 Refresh Token、不同的 JWT 各自互不影响

3. 过期判断方式 ⇧

  • 不需要在数据库中存储过期时间字段
  • 只需记录创建时间，过期判断：数据库无需单独存过期时间，只记录创建时间；
    • 7 天前创建即过期，3 天前创建即未过期；记录随机数和所属用户即可
    • 用当前时间减去创建时间即可判断是否过期（如创建于 7 天前 → 过期；3 天前 → 未过期）。

4. 控制自动续期的设备数量 ⇧

  • 续期数量限制示例：
    • 假设同一用户只允许 3 个设备自动续期。
    • 创建第 4 个 Refresh Token 时，检查是否已有 3 个有效的记录
    • 可选策略一：拒绝创建第 4 个。
    • 可选策略二：创建第 4 个的同时，将最早的（第 1 个）标记失效或从数据库删除
    • 被删除的 Refresh Token 下次续期时会被判定为不合法，该设备需重新登录 踢下线
  • 设备数量限制可配置，不写死在代码中

5. JWT 与 Refresh Token 的有效期设计原则

对比项 JWT RefreshToken
用途 用户认证（每次请求都带） JWT 过期后自动续期
标准 有标准（JWT spec） 无标准，自行设计
使用频率 极高（每次刷新页面都用） 低（仅在 JWT 过期时用）
有效期 短（如 2 小时） 较长（如 7 天、14 天，不宜超过一个月）
存储 无状态，不存数据库 有状态，存数据库
  • JWT 有效期必须短：因为使用频繁，被黑客截获的概率大；有效期短可将风险窗口控制在 2 小时内。
  • RefreshToken 有效期可稍长：使用频率低，被截获概率小；但不宜过长（如一个月以上），否则一旦泄露风险极大。
  • 重置机制：
    • 网站可提供”重置”按钮，用户点击后清除该用户所有已下发的 Refresh Token，使黑客窃取的 Refresh Token 立即失效
    • 必须实现”退出登录”按钮，用户点击后清除该用户所有已下发的 Refresh Token，使黑客窃取的 Refresh Token 立即失效
    • 或者提供用户自行可选择退出其他设备登录的功能，用户点击后清除该用户在其他设备上已下发的 Refresh Token 立即失效

6. 登录数量控制与续期数量控制的区别，为什么控制续期数而非登录数 ⇧

  • 服务器控制的是自动续期数量，不是同时登录数量。
  • JWT 无状态，无法控制登录数量：JWT 下发后，服务端不记得发过多少，也没有存入数据库，不知道用户同时在线多少
  • 登录后两小时必然会续期，因此直接控制续期数量等价于控制设备数，且实现成本更低。
  • 控制 Refresh Token 比控制 JWT 合算
    • 若控制 JWT，需把所有 JWT 存入数据库；JWT 下发频繁会导致表数据膨胀，没有必要

7. 补充说明：RefreshToken 的两种实现方式

  1. 随机字符串（有状态）：

    • 生成一个随机数存入数据库（代码示意：bin/rails c在控制台中，SecureRandom.hex生成随机数）。
    • 优点：可主动删除/失效下发的 Refresh Token，控制能力强（如限制设备数、提供重置功能）。
    • 缺点：需要维护数据库表。

  2. 另一种 JWT（无状态）：

    • 用 JWT 格式生成 Refresh Token，payload 可为空对象或仅标注用途（如 {"type": "refresh"}）。
    • 优点：无需数据库表，天然无状态，不占用数据库空间。
    • 缺点：无法主动失效，签发后在有效期内一直有效，无法做设备数控制或重置。
  • 推荐方案：
    • JWT 本身保持无状态（使用太频繁，存数据库浪费空间）；
    • Refresh Token 采用有状态方案存入数据库，便于主动控制（删除、重置等）。

简要结论 ⇧

  • JWT 有标准、服务端不存储
  • Refresh Token 无标准、是服务端自行设计实现落库（数据库或 Redis），以便校验合法性与进行管控，与 JWT 独立的续期凭证
  • 核心目的是在 JWT 过期后自动获取新 JWT，避免频繁重新登录用户体验差
  • Refresh Token 自身过期才需要重新登录
  • 其设计需关注三点：
    • 有效期比 JWT 长但不宜过长
    • 通过数据库记录创建时间判断过期
    • 通过数据库记录数量控制自动续期设备数
  • 服务端只能管控 Refresh Token 的数量，进而间接管控自动续期的设备数量；
  • 两类 Token 按使用频率分配有效期长度，并可通过重置清空兜底
  • 推荐 JWT 保持无状态、Refresh Token 采用有状态（存数据库），以兼顾性能与可控性

注意事项 ⇧

  • 不同设备、不同浏览器必须下发不同的 Refresh Token，不能共用。
  • Refresh Token 表只需记录随机数、所属用户、创建时间；过期状态由创建时间推算，无需单独存过期时间。
  • Refresh Token 有效期不要超过一个月。
  • 可预留重置按钮：一键清空该用户所有已下发的 Refresh Token。

require "jwt"

class Api::V1::SessionsController < ApplicationController
  # 创建会话
  # @return [String] jwt
  # @return [String] errors
  # @return [Integer] status
  def create
    # 如果是测试环境，则跳过验证码查找
    if Rails.env.test?
      return render status: :unauthorized, json: { errors: "邮箱或验证码错误" } if
        params[:code] != "123456"
    else
      canSignIn = ValidationCode.exists? email: params[:email],
        code: params[:code], used_at: nil
      return render status: :unauthorized, json: { errors: "邮箱或验证码错误" } unless canSignIn
    end
    user = User.find_or_create_by email: params[:email]
    render status: :ok, json: { jwt: user.generate_jwt }
  end
end
